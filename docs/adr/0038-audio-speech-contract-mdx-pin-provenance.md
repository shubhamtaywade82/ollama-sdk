# ADR 0038: Second post-audit refresh — /v1/audio/speech recorded as a generation-excluded contract operation, MDX pin provenance, and the drift-anchor correction

**Status**: Accepted
**Date**: 2026-10-23
**Context**: The second daily audit against the v1.20.0 baseline (`1ed8f92`) again led with a "zero upstream drift" headline — this time anchored on `d9b8601`, a pin retired two releases ago, while simultaneously verifying the v1.20.0 release that absorbed exactly the two commits (`2476d5e`, `36a6e99`) that had landed after it. The report's release/registry facts and its four cited docs surfaces checked out; the anchor and two of its omissions did not.

## Context

Three verified findings drove this refresh:

1. **In-window documentation drift the audit missed.** Upstream `6ef847b8` ("mlxrunner: add Phonon text-to-speech support", 2026-10-22 18:36 UTC — inside the audit's own 24-hour window) added a `### /v1/audio/speech` section to the OpenAI-compatibility page: added in Ollama v0.40.8, `model`/`input` (≤ 4,096 chars)/`voice`/`response_format` (`wav` default, `pcm`; `mp3`/`opus`/`aac`/`flac` unsupported)/`speed` (`1` only)/`stream_format` (`audio` only) supported, `instructions` unsupported, 16-bit mono 24 kHz audio, unsupported values rejected with `400` rather than ignored. The endpoint is **absent from upstream's own `openapi.yaml`** (docs ahead of spec), so no openapi re-pin was required — but the endpoint exists in the documentation surface the contract system is obliged to track.

2. **The MDX pins carried no provenance at all.** `docs/upstream/ollama-openai-compatibility.mdx` was pinned 2026-10-11 and sat 11 days stale while the audio section landed; `docs/upstream/ollama-anthropic-compatibility.mdx` missed upstream `33a3afa6` (2026-10-13, "changing model recs to Models page link"), which dropped the "Recommended local models" list. Nothing consumed any pin date for these files, no test covered their freshness — the exact defect class ADR 0036 fixed for the openapi pin's `docs-index.json` entry, repeating in the two remaining sources.

3. **The anchor correction.** "Track for commits after `d9b8601`" is the wrong instruction going forward: `2476d5e` and `36a6e99` landed after that pin and were absorbed by v1.20.0's re-pin to `36a6e99`. Anchoring tomorrow's audit on the retired pin would re-flag absorbed drift as new. The live openapi content hash matches the `36a6e99` pin byte-for-byte (raw upstream sha256 `e94c8f02…`, unchanged since the v1.20.0 refresh), so `36a6e99` is the correct baseline; no patch release was required for it.

## Decisions

1. **Refresh both MDX pins with SHA-bearing headers, mirroring the openapi discipline.** `scripts/refresh-mdx-pins.ts` re-pins both files from the live `docs.ollama.com` markdown twins (base64 payloads elided per the standing convention). Each header's second line is now machine-parseable — `Pinned from <url> on <date> (source SHA: <40-hex>).` — where the SHA is the last upstream commit touching the repo's `docs/api/*.mdx` source (`6ef847b8…` for openai, `33a3afa6…` for anthropic). The rendered twin differs from that source in site plumbing only (llms.txt preamble, unwrapped CodeGroup components, `.md` link suffixes), which the header records; all three differences are parse-neutral for `discoverFromMdx` and the parity verifier's checkbox matchers. `docs-index.json` gains `pinnedSha`/`pinnedAt` for both mdx sources, and `test/contract/pin-consistency.test.ts` asserts header/index agreement, refresh-content markers (the openai pin must contain the audio section; the anthropic pin must not contain the retired model list), and base64 elision — a stale MDX pin can no longer hide behind a passing build, closing the last untracked source.

2. **`/v1/audio/speech` is declared in the IR and excluded from generated code — the `createBlob` precedent.** The bidirectional discovery validator forces the declaration: once the refreshed MDX pin is in place, `/v1/audio/speech` is a *discovered* endpoint, and Direction 2 ("every discovered endpoint must be declared") hard-fails without an overlay entry. So `contracts/overlays/openai.yaml` declares `openaiAudioSpeech` (POST, local+cloud, `compatibility.minVersion: '0.40.8'`, `status.experimental: true`, `streaming: unsupported` — the contract's streaming flag describes SDK transport capability within the declared modes json/ndjson/sse, and a raw audio byte stream fits none of them, exactly like `createBlob`; the endpoint's streaming nature is recorded in the notes and the docs matrix) with a full `parity.request` matrix — six supported fields, `instructions` unsupported, four nested unsupported `response_format` values — typed against the new hand-written `OpenAISpeechRequest`. But the generated runtime's transports are `json`/`ndjson`/`sse`; a raw 16-bit mono audio byte stream fits none of them. Following `createBlob` (binary *request* body) and the web-ops host exclusion, the operation is filtered out of the generated `OpenAIApi` class (`BINARY_BODY_OPS` in `generator/emitters/typescript/api.ts`) and out of MCP tools (`BINARY_TRANSPORT_MCP_EXCLUSIONS` in `generator/emitters/mcp/tools.ts` — renamed from `BINARY_BODY_MCP_EXCLUSIONS` to cover both cases; the two sets must stay in sync, and a test asserts it). The `OperationDefinition` constant is still emitted for IR visibility, so discovery, drift, and metadata stay complete. Advertising an audio endpoint as an executable MCP tool would mislead consumers into calling a tool that cannot actually perform the operation.

3. **The typed request shape is exported, not hidden.** `src/integrations/openai.ts` gains `OpenAISpeechRequest` (broad: full OpenAI `response_format`/`speed` unions typed for drop-in interop, with `@remarks` recording that Ollama rejects unsupported *values* with `400` — unlike the usual accept-and-ignore contract — and `instructions` typed-but-ignored) and the strict `OllamaOpenAISpeechRequest` (`wav`/`pcm` only, `speed: 1` only, no `instructions`), matching the broad/strict pattern of the Chat and Embeddings surfaces. Callers driving the endpoint over their own HTTP layer before an SDK audio transport lands get a documented, parity-verified type instead of `Record<string, unknown>`.

4. **No client method, no transport work, this release.** An audio transport (a `TransportMode` that returns the response body as bytes) is a real feature with runtime, edge-runtime, and telemetry implications — deliberately out of scope. The contract now records the endpoint honestly (documented, experimental, generation-excluded) so the future work has a typed anchor, and so the next audit's "documentation alignment" check cannot claim parity for an endpoint the contract system never saw.

## Consequences

- Version 1.22.0 (minor): additive surface only — two exported types, refreshed pins, contract metadata. No runtime behavior changes; no generated API changes (the audio op is excluded from generation by design).
- Tests: 8 net-new — five MDX pin-consistency tests and three audio-contract tests (IR declaration with full metadata, OperationDefinition-emitted-but-API-method-excluded, MCP exclusion with the createBlob sync guard).
- Contract gates: 27 operations declared, 26 discovered, no drift (the refreshed openai pin contributes `/v1/audio/speech` to discovery); drift-strict 100 matched / 0 unexpected; parity now verifies the audio field matrix structurally (against `OpenAISpeechRequest`) and live (against the docs section) — 18 operations total, structural + live-docs. The nested-unsupported verification learned the docs' actual evidence format: upstream documents nested value restrictions as unchecked checkbox items under a supported parent (`* [ ] \`mp3\`, \`opus\`, \`aac\`, \`flac\`` under `* [x] \`response_format\``); the verifier now accepts checkbox evidence for nested leaves (an unchecked line mentioning the leaf), not just "Not supported" sections — an additive change, so the Anthropic `cache_control` evidence path is unaffected.
- Process lesson recorded alongside ADR 0036's display-artifact trap: the first push of this branch failed CI on `contract:validate` even though the local run had "passed" — the local command was piped (`npm run contract:validate | tail`), so the pipeline's exit code was `tail`'s, not the validator's, and the `✗ openai.yaml` line scrolled away above the tail window. Gate runs must check the tool's own exit code (`set -o pipefail`, or no pipe) — a green-looking tail is not a green gate. The CI failure itself was the validator catching `streaming: supported` + `transport: json` on the audio op (streaming operations must use ndjson or sse) — the invariant working exactly as designed, which is what corrected the flag to its honest value.
- Declined alternatives, with reasons: (a) adding `/v1/audio/speech` to the pinned `openapi.yaml` as a curated addition (the System One pattern) — that path exists for endpoints whose request/response the *spec* will carry; generating a real op here would emit a callable method the runtime cannot transport, a footgun the loud-failure guard would only convert into a runtime error; (b) adding a binary `TransportMode` — real feature, wrong release; (c) not refreshing the MDX pins until upstream's openapi.yaml catches up — that is exactly the "documentation alignment" blind spot this ADR closes; (d) recording the audio endpoint only in overlay `notes` without the IR declaration — the discovery validator forbids it by construction.
- Watch items carried forward, not acted on: upstream `816c36ac` ("openai: preserve failures in Responses streams") and `e61ba8b4` ("openai: finish reasoning before client tool calls") — both code-ahead-of-docs on the OpenAI bridge; `a79f7d74` ("anthropic: reuse resolved thinking for web search") and the standing `efabf6bc` Anthropic mid-stream error-events item — the pinned MDX still matches the docs (streaming error events unsupported), and the contract rule remains: pin what the *documentation* says, re-audit when the docs row flips. Tomorrow's audit must anchor drift tracking on `36a6e99` for the openapi spec and `6ef847b8`/`33a3afa6` for the two MDX pins — never on the retired `d9b8601`.
